## Lab Overview
This lab covers the implementation of a comprehensive monitoring strategy. It demonstrates how to move beyond basic metrics to deep infrastructure and application visibility using the Amazon CloudWatch suite and AWS Config.

## Task 1: Installing and Configuring the CloudWatch Agent

Standard EC2 metrics only see the "outside" of a virtual machine. To monitor **Memory** and **Application Logs**, we must install the **CloudWatch Agent**.

### 1.1 Deploying the Agent via Systems Manager (SSM)
Instead of manual installation, we use **SSM Run Command** for automated deployment:
1.  Navigate to **Systems Manager** -> **Run Command**.
2.  Document: `AWS-ConfigureAWSPackage`.
3.  **Command Parameters:**
    * **Action:** `Install`
    * **Name:** `AmazonCloudWatchAgent`
    * **Version:** `latest`
4.  **Targets:** Manually select the **Web Server**.
5.  Click **Run** and wait for the `Success` status.

### 1.2 Centralized Configuration (Parameter Store)
We store the agent's configuration in the **SSM Parameter Store** so it can be reused by multiple instances.
1.  **Parameter Name:** `Monitor-Web-Server`.
2.  **Value (JSON):**
```json
{
  "logs": {
    "logs_collected": {
      "files": {
        "collect_list": [
          {
            "log_group_name": "HttpAccessLog",
            "file_path": "/var/log/httpd/access_log",
            "log_stream_name": "{instance_id}",
            "timestamp_format": "%b %d %H:%M:%S"
          }
        ]
      }
    }
  },
  "metrics": {
    "metrics_collected": {
      "mem": { "measurement": ["mem_used_percent"], "metrics_collection_interval": 10 },
      "disk": { "measurement": ["used_percent"], "resources": ["*"], "metrics_collection_interval": 10 }
    }
  }
}
```

### 1.3 Activating the Agent
Run the `AmazonCloudWatch-ManageAgent` command via SSM:

* Optional Configuration Source: `ssm`
* Optional Configuration Location: `Monitor-Web-Server`

## Task 2: Log Monitoring & Alarm Creation

En esta fase, transformamos datos no estructurados (texto de logs) en métricas legibles para la toma de decisiones.

### 2.1 Metric Filters (Texto a Números)
Configuramos un filtro para identificar errores **404 Not Found** en el archivo de acceso del servidor web:
1. **Log Group:** `HttpAccessLog`.
2. **Filter Pattern:** `[ip, id, user, timestamp, request, status_code=404, size]`
   * *Lógica:* Este patrón le dice a CloudWatch cómo mapear cada columna del log de Apache y que solo cuente las líneas donde el código de estado sea exactamente 404.
3. **Metric Details:**
   * **Filter Name:** `404Errors`
   * **Metric Namespace:** `LogMetrics`
   * **Metric Value:** `1` (Cada coincidencia suma 1 a la métrica).

### 2.2 Alarms & Notifications (SNS)
Creamos una respuesta automática ante comportamientos inusuales:
1. **Alarm Condition:** Se activa cuando `404Errors >= 5` en un periodo de **1 minuto**.
2. **Action:** Configuración de un **Amazon SNS Topic**.
3. **Validation:** Al intentar acceder repetidamente a páginas inexistentes (ej. `/start2`), el sistema detectó el pico de errores y envió una notificación automática al correo electrónico configurado.

## Task 4: Real-Time Event Notifications

Utilizamos **Amazon EventBridge (CloudWatch Events)** para detectar cambios operativos en tiempo real.

1. **Event Rule:** `Instance_Stopped_Terminated`.
2. **Event Pattern:** 
```json
   {
     "source": ["aws.ec2"],
     "detail-type": ["EC2 Instance State-change Notification"],
     "detail": {
       "state": ["stopped", "terminated"]
     }
   }
```

3. **Target:** El evento se enruta al SNS Topic, permitiendo que el equipo de operaciones sepa instantáneamente si un servidor crítico ha sido detenido o eliminado.

## Task 5: Monitoring for Infrastructure Compliance (AWS Config)

En esta fase, utilizamos **AWS Config** como un "auditor automatizado" que evalúa si los recursos de nuestra infraestructura cumplen con las políticas de gobernanza y control de costos de la organización.

### 5.1 Initial Configuration
1.  Navegamos a **AWS Config** y activamos el servicio mediante el botón **Get started**.
2.  Configuramos la grabación de todos los recursos soportados en la región para permitir un rastreo histórico completo.

### 5.2 Implementing Governance Rules
Añadimos reglas gestionadas por AWS para auditar dos áreas críticas:

1.  **Regla de Etiquetado (`required-tags`):**
    * **Propósito:** Asegurar que todos los recursos tengan una etiqueta de identificación.
    * **Configuración:** Establecimos el parámetro `tag1Key` como `project`.
    * **Lógica:** Cualquier recurso que no tenga la etiqueta `project` será marcado automáticamente como **Non-compliant** (No cumple).

2.  **Regla de Optimización de Costos (`ec2-volume-inuse-check`):**
    * **Propósito:** Identificar volúmenes EBS que están "huérfanos" (no conectados a ninguna instancia).
    * **Impacto:** Esto permite eliminar almacenamiento que genera costos sin estar siendo utilizado.

### 5.3 Compliance Audit Results
Tras la evaluación, analizamos los resultados en el panel de **Rules**:
* **Web Server:** Aparece como **Compliant** porque ya contenía el tag `project`.
* **Recursos Varios:** Aparecen como **Non-compliant**, proporcionando una lista de acción inmediata para que el equipo de CloudOps corrija las etiquetas o elimine volúmenes sin uso.


## 💡 Expert Pro-Tips for Monitoring & Compliance

* **Cost Optimization via Config:** AWS Config es una herramienta poderosa para el ahorro. Reglas como `ec2-volume-inuse-check` o `unused-reserved-instances` pueden ahorrar miles de dólares al identificar recursos abandonados.
* **Infrastructure Snapshot:** AWS Config no solo audita, sino que mantiene una "línea de tiempo" de cada recurso. Esto es vital en análisis forenses o auditorías de seguridad para saber exactamente qué cambió y quién lo cambió.
* **Auto-Remediation:** Una característica avanzada de AWS Config es la **Remediación Automática**. Podrías configurar una regla para que, si encuentra un volumen EBS sin cifrar, dispare una función Lambda que lo cifre o lo elimine automáticamente.
* **Event-Driven Monitoring (Task 4 vs 5):** Mientras que **CloudWatch Events** reacciona instantáneamente a cambios de estado (ej. "la instancia se detuvo"), **AWS Config** se enfoca en el cumplimiento de la configuración (ej. "¿esta instancia tiene el tamaño permitido?"). Ambos son complementarios.
* **Escalabilidad del Agente:** En entornos de producción, el CloudWatch Agent no se instala manualmente. Se integra en la **AMI Dorada** (Task 1 del Lab anterior) o se despliega masivamente usando **Systems Manager State Manager**.
