# Lab 266: Troubleshooting a Network Issue
**Course:** AWS re/Start | **Module:** Networking / Troubleshooting

## Objective
The objective of this lab is to diagnose and resolve connectivity issues in a pre-existing AWS infrastructure. As a Cloud Support Engineer, the task involves identifying why an Apache (httpd) web server is unreachable via HTTP and ICMP (ping), despite the service being active on the instance.

## Key Concepts

* **The OSI Model & Troubleshooting:** Identifying if an issue is at the Network Layer (Routing/NACLs) or the Application/Transport Layer (Security Groups/Service status).
* **Service Management (systemctl):** The standard Linux utility for controlling the state of services (start, stop, status) in systemd-based distributions.
* **Security Group Rules (Ingress/Egress):** Understanding that even if a service is running, AWS blocks all inbound traffic by default unless explicitly allowed.
* **ICMP Protocol:** The protocol used by the `ping` command, which is distinct from TCP (HTTP) and must be allowed separately in Security Groups.

## Step-by-Step Instructions

### 1. Connecting and Service Verification
Access the instance and verify if the web server is actually running.

1.  Connect to the instance via SSH:
    ```bash
    ssh -i labsuser.pem ec2-user@<public-ip>
    ```
2.  Check the status of the Apache service:
    ```bash
    sudo systemctl status httpd.service
    ```
3.  Start the service if it is inactive:
    ```bash
    sudo systemctl start httpd.service
    ```

> 📝 Technical Note: Service Persistence
> Running `systemctl start` only starts the service for the current session. To ensure Apache starts automatically after a reboot, you should run `sudo systemctl enable httpd.service`.

### 2. Identifying the Connectivity Gap
Despite the service being `active (running)`, the web page fails to load in the browser.

* **Test URL:** `http://<PUBLIC-IP>`
* **Result:** Connection Timeout.

### 3. Infrastructure Investigation
Navigate to the VPC Dashboard to audit the networking components:

1.  **Check Internet Gateway (IGW):** Verified as attached to the VPC.
2.  **Check Route Tables:** Verified that `0.0.0.0/0` points to the IGW.
3.  **Check Network ACLs:** Verified that inbound/outbound rules allow traffic (Rule 100: ALL ALLOW).
4.  **Check Security Groups:** * **The Issue:** The Security Group only allows SSH (Port 22). It is missing rules for **HTTP (Port 80)** and **ICMP (All)**.

### 4. Resolution and Testing
Modify the Security Group assigned to the EC2 instance:

1.  Go to **Security Groups** -> Select the instance's group.
2.  **Edit Inbound Rules:**
    * Add **HTTP** | Port 80 | Source: `0.0.0.0/0`
    * Add **All ICMP - IPv4** | Source: `0.0.0.0/0`
3.  Save rules.

> **Command explanation:** Adding "All ICMP" allows the `ping` command to receive an echo reply. Without this, the server is "stealth" even if the web service is working perfectly.

### 5. Final Validation
Verify the fix by reloading the browser and using the terminal.

* **Ping Test:** `ping <public-ip>` (Now receiving replies).
* **Web Test:** Refresh `http://<PUBLIC-IP>`.

## Pro-Tips for Real-World Scenarios

* 💡 **Pro-Tip: The "Bottom-Up" Troubleshooting Path:** When a resource is unreachable, check in this order:
    1. **OS Level:** Is the service running? (`systemctl status`)
    2. **Security Group:** Is the port open? (Instance level)
    3. **NACL:** Is the traffic allowed at the subnet level?
    4. **Routing:** Is there a route to the IGW?
* 💡 **Pro-Tip: Security Group "Source" Best Practice:** For a web server, Port 80/443 must be `0.0.0.0/0`. However, for administrative ports like SSH (22) or RDP (3389), never leave them open to the world. Use your specific IP.
* 💡 **Pro-Tip: Use `curl` for internal testing:** If you are inside the server and want to see if the website is working locally (ignoring AWS firewalls), run `curl -I localhost`. If it returns `200 OK`, the problem is definitely in the AWS Networking layer.

## Useful Commands

| Command | Purpose |
| :--- | :--- |
| `sudo systemctl status httpd` | Checks if the web server process is alive. |
| `sudo systemctl restart httpd` | Restarts the service (useful after configuration changes). |
| `curl -v http://localhost` | Verbose output of a local web request. |
| `ping 8.8.8.8` | Checks if the instance itself can reach the outside internet. |
