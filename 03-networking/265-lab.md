# Lab 265: Internet Protocol Troubleshooting Commands *

## Objective
Master the essential command-line tools used to diagnose networking issues in a Linux environment. This lab maps specific commands to the OSI (Open Systems Interconnection) model to provide a structured approach to troubleshooting connectivity, latency, and service availability.

## Key Concepts
* **ICMP (Internet Control Message Protocol):** The protocol used by `ping` to verify reachability.
* **TCP Handshake:** The process verified by `telnet` to ensure a port is open and listening.
* **Hops:** Each intermediate router or server that a packet passes through on its way to a destination (visualized via `traceroute`).
* **HTTP Status Codes:** The application-level responses (like 200 OK) captured via `curl`.

### Layer 3: Network (IP Connectivity & Routing)
Focuses on whether a packet can physically reach a destination.
* **`ping 8.8.8.8 -c 5`**: Tests basic reachability. The `-c` flag limits the requests to prevent infinite looping.
* **`traceroute 8.8.8.8`**: Maps the path to the destination.
    - **Pro-Tip:** If you see `***`, it indicates a "timed out" hop, meaning a router is either down or configured to ignore trace requests.

### Layer 4: Transport (Ports & TCP Connections)
Focuses on whether a specific service (like Web or SSH) is available.
* **`netstat -tlp`**: Shows which ports are currently "Listening" on your local machine.
* **`telnet [IP] [Port]`**: Attempts to establish a TCP connection to a remote port.
    - **Refused:** The server is up, but the port is closed or blocked by a firewall (Security Group).
    - **Timeout:** There is no route to the server, or a "silent" firewall is dropping the packets.

### Layer 7: Application (Web Traffic & Data Transfer)
Focuses on the actual data and protocol response.
* **`curl -vI https://aws.com`**: Fetches the HTTP headers from a website.
    - **`-v` (Verbose):** Shows the full handshake and request details.
    - **`200 OK`**: Confirms the web server is healthy and serving content.

## 💡 Pro-Tips for Network Troubleshooting

1. **The Order of Operations:** Always start at **Layer 3** (`ping`). If you can't ping the gateway, there’s no point checking the website (`curl`). Work your way up the OSI stack.
2. **Security Groups & ICMP:** In AWS, `ping` often fails by default because the **Security Group** does not allow "All ICMP" traffic. Always check your AWS rules before assuming the server is down.
3. **MTR (My Traceroute):** A professional alternative to `traceroute` is `mtr`. It combines ping and traceroute into a single, live-updating report.
4. **`netstat` vs `ss`:** On modern Linux systems, the `ss` command is faster and more powerful than the older `netstat`. Try `ss -tuln` for a similar output.

## Command Reference Summary

| Command | OSI Layer | Primary Purpose |
| :--- | :--- | :--- |
| `ping` | 3 (Network) | Verifies if a remote host is alive/reachable. |
| `traceroute` | 3 (Network) | Identifies where packets are being dropped or delayed. |
| `netstat -tp` | 4 (Transport) | Lists active TCP connections on the local host. |
| `telnet [IP] [Port]` | 4 (Transport) | Tests if a specific remote port is open/accessible. |
| `curl -v` | 7 (Application)| Tests web server responses and downloads content. |
