# Lab 175: Using Auto Scaling in AWS (Linux)

## Objective
Implement a highly available and self-scaling architecture. This lab demonstrates how to transition from a single manual EC2 instance to a dynamic fleet managed by an Application Load Balancer (ALB) and Auto Scaling Group (ASG).

## Key Concepts
* **AMI (Amazon Machine Image):** A "golden image" or snapshot of a configured server used as a template for new instances.
* **Launch Template:** A saved configuration that defines the AMI, instance type, and network settings for Auto Scaling.
* **Application Load Balancer (ALB):** Distributes incoming application traffic across multiple targets (EC2 instances) in different Availability Zones.
* **Auto Scaling Group (ASG):** A collection of EC2 instances that scales based on policies (e.g., CPU utilization).
* **Target Tracking Policy:** A scaling policy that keeps a specific metric (like 50% CPU) at a target value by adding or removing instances.

## 1.2 Setting up the CLI Environment
Before running commands, you must ensure the AWS CLI is configured with the correct region and context.

### Step 1. Identify your Lab Region:
Access the **Instance Metadata Service (IMDS)** via the link-local address `169.254.169.254`. This IP is only accessible from within the EC2 instance.
```bash
curl http://169.254.169.254/latest/dynamic/instance-identity/document | grep region
```
### Step 2. Configure AWS CLI:
Run the configuration wizard. When prompted, press Enter for the keys (as they are handled by an IAM Role), but specify the region you just identified and output format.
```bash
aws configure
# Access Key ID: [Press Enter]
# Secret Access Key: [Press Enter]
# Default region name: us-west-2 (or the region retrieved above)
# Default output format: json
```

## 1.3 Creating a New EC2 Instance (Prototype - Web Server)
We use `run-instances` with a **User Data** script to automate software installation.

### Step 3. Review Bootstrap Script:
Move to the directory containing the lab's automation assets `cd /home/ec2-user/`, then, view the contents of `UserData.txt`. This script installs Apache and PHP, but also performs critical sanitization commands to prepare the instance for imaging. This ensure AMI is clean and secure.
```bash
# Removes SSH keys and shell history to ensure a clean, secure AMI
find -wholename /root/.*history -wholename /home/*/.*history -exec rm -f {} \;
find / -name 'authorized_keys' -exec rm -f {} \; # <- Removes access keys
rm -rf /var/lib/cloud/data/scripts/* # <- Clears cloud-init history
```
📂 **Full Source File:** [UserData.txt](../assets/11/UserData.txt)

### Step 4. Provision Instance:
Run the following command (replace placeholders with values from the lab **Details** panel):
```bash
aws ec2 run-instances \
    --key-name KEYNAME \
    --instance-type t3.micro \
    --image-id AMIID \
    --user-data file:///home/ec2-user/UserData.txt \
    --security-group-ids HTTPACCESS \
    --subnet-id SUBNETID \
    --associate-public-ip-address \
    --tag-specifications 'ResourceType=instance,Tags=[{Key=Name,Value=WebServer}]' \
    --output text --query 'Instances[*].InstanceId'
```
* **`--query`**: This JMESPath expression filters the JSON response to return only the `InstanceId`.

### Step 5: Wait for Runtime
AWS commands are asynchronous. We must wait for the resource to be ready before proceeding. To ensure that we don't try to configure the instance before it will be ready, we use:
```bash
aws ec2 wait instance-running --instance-ids NEW-INSTANCE-ID
```
* **Purpose:** Blocks the terminal until the instance changes to a `Running` state. Escencial for CI/CD workflows.

### Step 6: Retrieve DNS for Testing
Once the instance is running, we check the DNS address to test the web server:
```bash
aws ec2 describe-instances --instance-id NEW-INSTANCE-ID --query 'Reservations[0].Instances[0].NetworkInterfaces[0].Association.PublicDnsName'
```
* Test URL: `http://[PUBLIC-DNS-ADDRESS]/index.php`.
* Note: Wait ~5 minutes for the PHP application to finish installing.

## Task 2: Building the Auto Scaling Infrastructure
In this stage, we transition from a single prototype instance to a **Multi-AZ (Availability Zone)** architecture. We will deploy a Load Balancer to handle traffic distribution and an Auto Scaling Group (ASG) to manage fleet elasticity.

## 2.1 Creating an Application Load Balancer (ALB)
The ALB serves as the "front door" of the application, receiving all user requests and distributing them to the back-end servers.

### Basic Configuration:
1. Navigate to the **EC2 Console** -> **Load Balancing** -> **Load Balancers**.
2. Choose **Create load balancer** -> **Application Load Balancer (Create)**.
3. **Name:** `WebServerELB`.

### Network Mapping:
1. **VPC:** Select `Lab VPC`.
2. **Mappings:** Select **both** Availability Zones listed.
   * For the first AZ, select `Public Subnet 1`.
   * For the second AZ, select `Public Subnet 2`.
   * *Architecture Note:* The Load Balancer must be in **Public Subnets** to receive traffic from the internet.

### Security Groups:
1. Remove the `default` security group.
2. Select `HTTPAccess`. This group is pre-configured to allow inbound traffic on **Port 80**.

### Listeners and Routing (Target Group):
The Load Balancer needs to know *where* to send the traffic.
1. Choose **Create target group** (opens a new tab).
2. **Target type:** `Instances`.
3. **Name:** `webserver-app`.
4. **Health Checks:** Set the path to `/index.php`. 
   * *Critical Concept:* The ALB will periodically "ping" this path. If the PHP app stops responding, the instance is marked as **Unhealthy** and traffic is rerouted.
5. Choose **Next** -> **Create target group**.
6. **Finalize ALB:** Return to the ALB tab, refresh the "Forward to" list, select `webserver-app`, and choose **Create load balancer**.
7. **Important:** Copy the **DNS Name** (e.g., `WebServerELB-123.us-west-2.elb.amazonaws.com`). This is the URL you will use to access your application.

The ASG is the brain of the operation, handling self-healing and dynamic scaling.

1. Select your new launch template and choose **Actions** -> **Create Auto Scaling group**.

3. **Network:**

   * Choose **webserver-app | HTTP** from your target groups.

## Task 4: Testing Auto Scaling (Scale-Out Event)
We will now intentionally overwhelm the CPU of our instances to trigger the Scaling Policy defined in Task 2.

### Step 1: Trigger the CPU Stress
1. Open a new browser tab and paste the **DNS Name** of the `WebServerELB` (the URL copied in Task 2.1).
2. Once the test page loads, choose **Start Stress**.
   * **What is happening?** This triggers a background process on the server that consumes 100% of the available CPU cycles.

### Step 2: Monitor the Scaling Activity
1. Return to the **EC2 Console** -> **Auto Scaling Groups**.
2. Select **Web App Auto Scaling Group**.
3. Choose the **Activity** tab.
4. **Observe the logs:** Within a few minutes, you will see a new entry: *"Launching a new EC2 instance"*.
   * **The Chain Reaction:** 1. The `stress` app spikes CPU to 100%.
     2. **Amazon CloudWatch** monitors this metric and detects that the fleet average has exceeded the **50% target**.
     3. CloudWatch triggers the **Scaling Policy**.
     4. The **ASG** launches a 3rd (and eventually 4th) instance to bring the average CPU back down to 50%.

## 💡 Expert Pro-Tips for Auto Scaling & CLI

### 1. AWS CLI & Automation (Task 1)
* **JMESPath Mastery:** The `--query` parameter uses **JMESPath**. Mastering this allows you to filter massive lists of resources and extract only the specific data (IDs, IPs, Tags) needed for your automation scripts.
* **Metadata Service (169.254.169.254):** This link-local IP is the foundation for instance auto-configuration. It allows a script to discover "who it is" and "where it is" (Region, Public IP, IAM Role) without hardcoding sensitive information.
* **AMI Sanitization:** **Never** create an AMI without clearing the `authorized_keys` and shell history. If you omit this, every instance launched from that AMI will inherit your credentials and activity logs, creating a significant security risk.

### 2. High Availability & Architecture (Task 2)
* **Multi-AZ Resilience:** By selecting subnets in different Availability Zones (AZs) for both the Load Balancer and the ASG, you ensure that even if an entire AWS Data Center goes offline, your application remains operational in the other zone.
* **The "Three-Tier" Pattern:** This lab follows the industry standard of **Public/Private Separation**. The entry point (ALB) is public, while the application servers (EC2) are shielded in private subnets. This drastically reduces the attack surface of your infrastructure.
* **Application-Aware Health Checks:** Standard EC2 checks only monitor hardware. Always use **ELB Health Checks** for web apps; they verify if your software (Apache/PHP) is actually responding, ensuring traffic is only sent to functional servers.

### 3. Scalability & Operational Excellence (Tasks 3 & 4)
* **Horizontal Scaling vs. Vertical:** Adding more instances (**Horizontal**) is superior to making one instance bigger (**Vertical**). It provides better fault tolerance and allows for seamless scaling without downtime.
* **The "Thermostat" Logic:** **Target Tracking** policies act like a thermostat. You set the "temperature" (e.g., 50% CPU), and AWS handles the complex math of adding or removing capacity to maintain that stable state.
* **Automatic Self-Healing:** The ASG doesn't just scale for traffic; it enforces your **Desired Capacity**. If an instance is manually terminated or crashes, the ASG will automatically launch a replacement to maintain the required number of servers.
* **Scale-In for Cost Control:** Elasticity works both ways. Once the "Stress Test" ends and CPU usage drops, the ASG triggers a **Scale-In** event to terminate extra instances, ensuring you only pay for the resources you actually need.
