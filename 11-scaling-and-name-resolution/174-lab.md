# Lab 174: Scaling and Load Balancing Your Architecture

## Objective
To design and deploy a fault-tolerant, highly available infrastructure that automatically adjusts capacity based on real-time CPU demand.

## Task 1: Creating a Custom AMI
To ensure all scaled instances are identical, we capture a "snapshot" of the existing configuration.

1.  **Selection:** In the **EC2 Console**, select `Web Server 1`.
2.  **Action:** `Actions` > `Image and templates` > `Create image`.
3.  **Config:** Name it `Web Server AMI` and set the description as `Lab AMI for Web Server`.
4.  **Verification:** Monitor the **AMIs** section in the left pane until the status is **Available**.

## Task 2: Implementing the Application Load Balancer (ALB)
The ALB serves as the single point of contact for clients, distributing traffic to prevent any single server from becoming a bottleneck.

1.  **Basic Config:** Create an **Application Load Balancer** named `LabELB`.
2.  **Network Mapping:** * Select `Lab VPC`. 
    * **Crucial:** Select both Availability Zones and map them to **Public Subnet 1** and **Public Subnet 2**.
3.  **Security:** Remove the default group and select `Web Security Group`.
4.  **Target Group:** * Create a new Target Group named `lab-target-group`.
    * **Target type:** `Instances`.
    * Set the protocol to `HTTP` on `Port 80`.
5.  **Finalize:** Go back to the ALB tab, refresh the listeners, and select `lab-target-group`. 
6.  **Data Retrieval:** Copy the **DNS Name** of the ALB (e.g., `LabELB-12345.us-west-2.elb.amazonaws.com`).

## Task 3: Creating the Launch Template
The Launch Template defines the "DNA" of the instances that the Auto Scaling Group will create.

1.  **Name:** `lab-app-launch-template`.
2.  **AMI:** Select the `Web Server AMI` created in Task 1.
3.  **Instance Type:** `t3.micro`.
4.  **Security:** Assign the `Web Security Group`.
5.  **Storage:** Keep the default `gp2` root volume settings.

---

## Task 4: Configuring the Auto Scaling Group (ASG)
The ASG maintains the health and number of instances in the fleet.

1.  **Basics:** Name it `Lab Auto Scaling Group` and link it to the `lab-app-launch-template`.
2.  **Network:** Select `Lab VPC` and **Private Subnet 1** & **Private Subnet 2**.
3.  **Advanced Options:** * Choose **Attach to an existing load balancer**.
    * Select `lab-target-group`.
    * **Health Check Type:** Change from `EC2` to **`ELB`**.
4.  **Scaling Limits:**
    * **Desired:** 2 | **Min:** 2 | **Max:** 4.
5.  **Scaling Policy:** Select **Target tracking scaling policy** using **Average CPU Utilization** with a Target Value of **50**.
6.  **Tagging:** Add a tag: Key: `Name` | Value: `Lab Instance`.

## Task 6: Stress Testing and CloudWatch Alarms
We simulate a peak-load event to observe the self-healing and scaling capabilities of the architecture.

1.  **Monitor Alarms:** In the **CloudWatch** console under **Alarms**, observe `AlarmHigh` (CPU > 50%) and `AlarmLow` (CPU < 50%).
2.  **Trigger Load:** On the "Load Test" web page, click **Load Test**. This initiates CPU-intensive calculations.
3.  **Observe Scaling:**
    * `AlarmHigh` will move into the **In alarm** state.
    * Return to the **EC2 Instances** page. You will see new instances being provisioned (Scale-Out) to bring the average CPU back down to 50%.
    * Once the load test stops, the ASG will eventually terminate the extra instances (Scale-In) to save costs.

## 💡 Expert Pro-Tips for Scaling

* **ELB Health Checks:** By switching to `ELB` health checks, the ASG replaces an instance if the **application** stops responding, even if the server is still "on." This is superior to `EC2` checks which only detect hardware/OS failure.
* **Launch Template Immutability:** Always use versioning in Launch Templates. If you update your app, create a new AMI, create a new Template Version, and then perform an **Instance Refresh** on the ASG to roll out the update without downtime.
* **Target Tracking:** Unlike "Simple Scaling," **Target Tracking** acts like a thermostat. It automatically calculates how many instances to add or remove to keep the metric (CPU) exactly where you want it.
* **Private Subnet Security:** Notice that the instances have NO public IPs. They are safe from the internet, yet accessible via the ALB. This is the **standard 3-tier architecture** best practice.
