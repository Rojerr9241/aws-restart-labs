# Lab 174: Scaling and Load Balancing Your Architecture
**Course:** AWS re/Start | **Module:** Scaling and Name Resolution

## Objective
The objective of this lab is to design and deploy a highly available and auto-scaling infrastructure. You will create a custom Amazon Machine Image (AMI), implement an Application Load Balancer (ALB) to distribute traffic, and configure an Auto Scaling Group (ASG) to automatically adjust capacity based on CPU demand, ensuring fault tolerance and cost optimization.

## Key Concepts

* **Application Load Balancer (ALB):** Operates at the Application Layer (Layer 7). It routes incoming traffic to multiple targets (EC2 instances) based on content and health checks.
* **Auto Scaling Group (ASG):** Automatically adds or removes EC2 instances to maintain a steady, predictable performance at the lowest possible cost.
* **Launch Template:** A configuration file that defines instance parameters (AMI, instance type, security groups) so the ASG knows exactly what to "clone" when scaling out.
* **AMI (Amazon Machine Image):** A pre-configured template that contains the software configuration (operating system, application server, and code) required to launch an instance.
* **Target Tracking Scaling Policy:** A scaling policy that increases or decreases the current capacity of the group based on a specific target value for a specific metric (e.g., maintain 50% average CPU).

## Step-by-Step Instructions

### 1. Custom Image Creation
Capture the state of a pre-configured web server to use as a baseline for scaling.

1.  Select **Web Server 1** -> **Actions** -> **Image and templates** -> **Create image**.
2.  **Image name:** `Web Server AMI`.
3.  Wait for the AMI status to become `Available`.

> 📝 Technical Note: AMI Immutability
> Once an AMI is created, it is immutable. If you update the code on the original server, you must create a new AMI and update your Launch Template to reflect the changes.

### 2. Application Load Balancer (ALB) Setup
Establish a single entry point for your users.

1.  **Create Load Balancer:** Choose **Application Load Balancer**.
2.  **Network Mapping:** Select `Lab VPC` and ensure both Availability Zones are selected with their respective **Public Subnets**.
3.  **Security Groups:** Select `Web Security Group`.
4.  **Listeners and Routing:** Create a new **Target Group** (`lab-target-group`) with "Instances" as the target type.
5.  Finalize the ALB creation and copy the **DNS Name** for testing.

> 📝 Technical Note: Public vs. Private Subnets
> The Load Balancer sits in the **Public Subnets** to receive internet traffic, but it will route that traffic to instances sitting in **Private Subnets**, enhancing security by hiding servers from direct internet access.

### 3. Auto Scaling Configuration
Define how and when your fleet should grow.

* **Launch Template:** Create `lab-app-launch-template` using the `Web Server AMI` and `t3.micro`. Assign the `Web Security Group`.
* **Auto Scaling Group (ASG):**
    * **Subnets:** Select **Private Subnet 1** and **Private Subnet 2**.
    * **Load Balancing:** Attach to the existing `lab-target-group`.
    * **Health Checks:** Change to **ELB** (this ensures that if the Load Balancer finds an instance unresponsive, the ASG will replace it).
    * **Group Size:** Desired: `2`, Min: `2`, Max: `4`.
    * **Scaling Policy:** Target tracking with **Average CPU Utilization** at `50`.

### 4. Load Testing and Validation
Simulate a traffic spike to trigger the CloudWatch alarms.

1.  Open the ALB **DNS Name** in your browser.
2.  Click **Load Test** to start intensive CPU calculations.
3.  Monitor **CloudWatch Alarms**:
    * `AlarmHigh` will transition from `OK` to `In alarm`.
    * The ASG will automatically launch new "Lab Instances" to handle the load.

> **Command explanation:** The Load Test application runs a loop of mathematical operations. This increases the `CPUUtilization` metric that CloudWatch tracks. Once the average stays above 50% for the defined period, the ASG triggers the "Scale Out" action.

## Pro-Tips for Real-World Scenarios

* 💡 **Pro-Tip: ELB Health Checks vs. EC2 Health Checks:** By default, ASG only replaces instances if the "Hardware" fails (EC2 check). By selecting **ELB Health Checks**, the ASG will also replace instances if the **Web Server (Apache/Nginx)** crashes, even if the VM is technically "running."
* 💡 **Pro-Tip: Warm-up Time:** When configuring scaling policies, consider the "Instance Warm-up" time. If set too short, the ASG might launch too many instances before the first ones have finished booting and started helping with the load.
* 💡 **Pro-Tip: Connection Draining (Deregistration Delay):** Always keep this enabled on your Target Group. It allows the Load Balancer to finish "in-flight" requests before terminating an instance during a "Scale In" event.

## Useful Commands

| Command | Purpose |
| :--- | :--- |
| `aws ec2 create-image` | (CLI) Creates an AMI from a running or stopped instance. |
| `aws autoscaling describe-auto-scaling-groups` | (CLI) Shows the current status, desired capacity, and health of your fleet. |
| `top` or `htop` | (Linux) Used inside the instance to verify that the Load Test is effectively hitting 100% CPU. |

## Cleanup

1.  **Delete the Auto Scaling Group:** This will automatically terminate all instances launched by it.
2.  **Delete the Load Balancer and Target Group.**
3.  **Deregister the AMI and delete the Snapshots:** AMIs and snapshots incur storage costs even if no instances are running.
4.  **Terminate Web Server 1.**
