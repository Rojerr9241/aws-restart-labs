# Lab 182: Working with Amazon EBS (Elastic Block Store)

## Objective
The goal of this lab is to manage the lifecycle of block storage in AWS. This includes creating new EBS volumes, mounting them in a Linux environment, performing data backups using Snapshots, and restoring data by creating new volumes from those snapshots.

## Key Concepts
* **EBS Volume:** Durable, block-level storage volumes that you can attach to running EC2 instances.
* **Snapshot:** An incremental backup of an EBS volume, stored in Amazon S3.
* **Mounting:** The process of making a storage device available to the operating system via a specific directory (mount point).
* **Availability Zone (AZ) Constraint:** An EBS volume must be in the same AZ as the EC2 instance to which it will be attached.

## Task 1 & 2: Creating and Attaching a Volume
EBS volumes are independent of the EC2 instance lifecycle, but they must share the same "location" to connect.

**Key Steps:**
1. **Identify AZ:** Check the AZ of the `Lab` instance (e.g., `us-west-2a`).
2. **Create Volume:** 1 GiB gp2 volume in the same AZ.
3. **Attach:** Link the volume to the instance using a device name like `/dev/sdb`.


## Task 3 & 4: File System Configuration (Linux)
A raw EBS volume is like a new unformatted hard drive. It needs a file system before it can store data.

**Commands & Workflow:**
1. **View Storage**: `df -h` (Initial check).
2. **Format Volume**:
    ```bash
    sudo mkfs -t ext3 /dev/sdb
    ```
3. **Create Mount Point**: `sudo mkdir /mnt/data-store`
4. **Mount & Persist**: 
    ```bash
    sudo mount /dev/sdb /mnt/data-store
    # Persist after reboot via /etc/fstab
    echo "/dev/sdb /mnt/data-store ext3 defaults,noatime 1 2" | sudo tee -a /etc/fstab
    ```
    > 📝 Technical Note: **Device Name** - Although we attach as `/dev/sdb`, modern Nitro-based instances often rename these internally to `/dev/nvme1n1`. The `df -h` command helps confirm the actual kernel name.


## Task 5: Data Protection with Snapshots
Snapshots allow us to capture the state of a volume at a specific point in time.

Workflow:

1. Create a file: `file.txt` inside `/mnt/data-store`.
2. Take Snapshot: Select volume -> Create snapshot.
3. Test Deletion: Delete the file manually (`sudo rm ...`) to simulate data loss.


## Task 6: Restoring Data
To recover the deleted file, we don't "copy" it back; we recreate the infrastructure from the backup.

**Recovery Steps**:

1. **Restore**: Create a new volume from the snapshot.
2. **Attach**: Attach this new volume to the EC2 instance as `/dev/sdc`.
3. **Mount**:
    ```bash
    sudo mkdir /mnt/data-store2
    sudo mount /dev/sdc /mnt/data-store2
    ```
4. **Verify**: Check that file.txt exists in the new mount point.

## 💡 Pro-Tips for Real-World Scenarios

1. **Snapshots are Incremental**: Only the blocks that have changed since the last snapshot are saved. This saves costs and time.

2. **AZ Migration**: To move an EBS volume to a different AZ or Region, you must take a snapshot first, then "Create Volume" or "Copy Snapshot" to the new destination.

3. **EBS Types: - gp2/gp3**: General purpose (System boots, small DBs).
    * io1/io2: High performance (Large active databases).
    * st1/sc1: Magnetic (Big data, logs, infrequent access).
