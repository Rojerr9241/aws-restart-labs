# Lab 241: Administrative Services and Monitoring ✅

## Objective
The goal of this lab is to manage system services using `systemctl` and explore infrastructure monitoring. This involves starting a web server (Apache), simulating a high CPU workload, and visualizing the performance impact using AWS CloudWatch.

## Key Concepts
* **systemd / systemctl:** The standard service manager in Linux used to start, stop, and check the status of background processes (daemons).
* **httpd (Apache):** A popular, open-source HTTP server that serves web content to users.
* **AWS CloudWatch:** A monitoring and observability service that provides data and actionable insights for AWS resources.
* **Stress Testing:** The process of deliberately increasing resource consumption (CPU/Memory) to evaluate system behavior under load.

## Task 2: Managing the httpd Service
Web servers run as background services. Managing their lifecycle is a core task for SysOps.

**Workflow and Commands:**
1. **Check Status:** Verify if the service is active.
   ```bash
   sudo systemctl status httpd.service
   ```
2. Start Service: If the status is "inactive (dead)", initiate the process.
    ```bash
    sudo systemctl start httpd.service
    ```
3. External Verification: Accessed the server via the browser using the `http://<public-ip>`. The appearance of the **Apache Test Page** confirms the server is reachable over the network (Port 80).

4. Stop Service: `sudo systemctl stop httpd.service`.

## Task 3: Linux Instance Monitoring and Stress Testing
This task demonstrates the difference between local monitoring (top) and cloud-based monitoring (CloudWatch).

1. Local Monitoring
Running `top` provides immediate feedback on process utilization. By executing a stress script in the background:
    ```bash
    ./stress.sh & top
    ```
    * **Result:** The CPU utilization spikes significantly (e.g., ~14% per process or higher) as the script consumes resources for a set duration (6 minutes).

2. Cloud Monitoring with AWS CloudWatch
CloudWatch aggregates data over time, providing a historical view of performance.

**Steps in Console:**
1. Navigate to **CloudWatch** > **Dashboards** > **Automatic Dashboards** > **EC2**.
2. Analysis: The "CPU Utilization" graph displays a clear peak corresponding to the execution of stress.sh.
3. Data Granularity: By default, CloudWatch for EC2 collects data in 5-minute intervals (Standard Monitoring). This explains why there might be a slight delay before the peak appears in the dashboard.

## 💡 Pro-Tips for Service & Monitoring
1. **Enable on Boot:** If you want a service (like `httpd`) to start automatically every time the server reboots, use:

```bash
sudo systemctl enable httpd.service
```
2. **Detailed Monitoring:** AWS offers Detailed Monitoring for EC2, which increases data frequency to 1-minute intervals for a small additional cost.

3. **CloudWatch Alarms:** In production, you wouldn't watch the graph manually. You would set a CloudWatch Alarm to notify you via email (SNS) if CPU exceeds a threshold (e.g., >80%).

4. **Journalctl:** If a service fails to start, use `sudo journalctl -u httpd` to see detailed error logs for that specific service.

## Command Reference Summary

| Command | Action |
| :--- | :--- |
| `systemctl status [service]` | Checks the current state (active/inactive) of a system service. |
| `systemctl start [service]` | Starts a service immediately in the current session. |
| `systemctl stop [service]` | Safely shuts down a running service. |
| `systemctl enable [service]` | Configures a service to start automatically on system boot. |
| `top` | Provides a dynamic, real-time view of CPU and Memory consumption. |
| `./script.sh &` | The `&` symbol runs the command in the background, freeing the prompt. |
| `q` | Exits the `top` monitor and returns to the command line. |
