# Lab 276: Network Hardening and Vulnerability Management

## Objective
Implement a proactive security posture by using **Amazon Inspector** to discover, analyze, and remediate security vulnerabilities within AWS Lambda functions. The lab focuses on identifying outdated software packages and automating the scan-to-fix lifecycle.

## Key Concepts
* **Vulnerability Scanning:** The process of inspecting resources for known security weaknesses.
* **CVE (Common Vulnerabilities and Exposures):** A standardized list of publicly disclosed cybersecurity vulnerabilities (e.g., CVE-2023-32681).
* **Remediation:** The act of fixing or "patching" a vulnerability to reduce risk.
* **Continuous Scanning:** Amazon Inspector automatically triggers a new scan every time a Lambda function is redeployed.

## Task 1: Activating Amazon Inspector
Amazon Inspector is a vulnerability management service that continually scans AWS workloads for software vulnerabilities and unintended network exposure.

**Instructions:**
1.  **Navigate:** In the AWS Management Console search bar, type and select **Inspector**.
2.  **Activation:** On the landing page, choose **Activate Inspector**.
    * *Technical Note:* Activation enables the service-linked roles required for Inspector to "reach into" other services like Lambda, EC2, and ECR to perform scans without manual agent installation.
3.  **Dashboard Monitoring:** Wait for the scan to initiate. Refresh the page periodically until the **Environment coverage** for **Lambda functions** shows **100%**.
4.  **Initial Scan:** Inspector automatically discovers supported resources in the account and begins an initial assessment immediately upon activation.

---

## Task 2: Analyzing and Interpreting Findings
Once the scan is complete, Inspector produces "Findings"—detailed reports of discovered security risks categorized by severity.

**Task 2.1: Reviewing Lambda Vulnerabilities**
1.  **Access Findings:** In the left navigation pane, under **Findings**, choose **All findings**.
2.  **Identify High-Risk Items:** You will see a list of Common Vulnerabilities and Exposures (CVEs). Locate the specific finding: **`CVE-2023-32681 - requests`**.
3.  **Deep Dive:** Select the radio button for this finding to open the details pane.
    * **Severity:** Note it is marked as **Medium**.
    * **Impacted Resource:** Identifies the specific function (e.g., `get-request`).
4.  **External Validation:** Click the external link next to the **Vulnerability ID**.
    * *Insight:* This leads to the **National Vulnerability Database (NVD)** maintained by NIST. Reviewing this ensures you understand the technical nature of the exploit, such as how an outdated `requests` package might handle data insecurely.
5.  **Remediation Advice:** Look at the **Remediation** section in the Inspector pane. It explicitly recommends upgrading the vulnerable package version to resolve the risk.

---

## Task 3: Remediating Vulnerabilities
Remediation is the process of fixing the security gap. In a serverless environment, this usually involves updating code dependencies in your deployment package.

**Task 3.1: Updating the Lambda Package**
1.  **Navigate to Lambda:** Search for and select the **Lambda** service.
2.  **Select Function:** Choose the **`get-request`** function from the list.
3.  **Edit Dependencies:** * In the code editor, open the **`requirements.txt`** file.
    * Locate the line: `requests==2.20.0`.
    * **Change to:** `requests` 
    * *Technical Note:* Removing the version number forces AWS Lambda to install the latest, patched version of the package during the build process.
4.  **Deploy Changes:** Click the **Deploy** button.
    * *Trigger Logic:* The act of deploying a new version of the function acts as an automatic **trigger** for Amazon Inspector to initiate a new scan of the resource.

---

## Task 4: Verification of Remediation
A critical step in any security workflow is verifying that the fix was successful and that the vulnerability is no longer "Active."

1.  **Return to Inspector:** Navigate back to the **Amazon Inspector** console.
2.  **Check Status:** Under **Findings**, choose **All findings**.
3.  **Filter by Status:** Change the **Finding status** filter from **Active** to **Closed**.
4.  **Confirmation:** Locate `CVE-2023-32681`. Its presence in the "Closed" list confirms that Inspector re-scanned the code, detected the updated package, and cleared the vulnerability.
5.  **Audit Trail:** Under **Resource coverage** > **Lambda functions**, check the **Last scanned** timestamp to verify the scan occurred immediately after your deployment.

## 💡 Expert Pro-Tips for Amazon Inspector

* **Continuous Scanning:** Unlike traditional security tools that require a "scheduled scan," Amazon Inspector is **event-driven**. It reacts to changes (new EC2 instances, ECR image pushes, or Lambda deployments) in real-time.
* **Inspector Score:** Inspector doesn't just give you a generic CVE; it provides a tailored **Inspector Score**. This score adjusts the standard CVSS base score by considering your specific environment (e.g., if the resource is reachable from the internet, the risk score increases).
* **Software Bill of Materials (SBOM):** You can export a consolidated SBOM from Inspector to see every single library and dependency used across your entire AWS environment, which is vital for compliance.
* **Suppression Rules:** In production, if a vulnerability is deemed an "acceptable risk" or a "false positive" by your security team, you can create **Suppression Rules** to filter those findings from your primary dashboard.

## 💡 Pro-Tips for Security Hardening

1. **The "Shift Left" Approach:** Using Amazon Inspector during development (before code reaches production) is called "Shifting Left." It’s cheaper and safer to fix bugs early.
2. **Standard vs. Code Scanning:** Inspector can scan both **Package Dependencies** (like our lab) and the **Actual Application Code** for logic flaws like injection or data leaks.
3. **Automation with EventBridge:** In professional environments, you can link Inspector to **Amazon EventBridge**. This allows you to send an automatic Slack or Email alert to developers the moment a new vulnerability is found.
4. **Suppression Rules:** Sometimes a vulnerability is a "false positive" or isn't reachable in your environment. You can create **Suppression Rules** to hide these findings and keep your dashboard clean.
