# Lab 280: Malware Protection Using AWS Network Firewall

## Objective
Harden the network perimeter of AnyCompany by implementing a stateful firewall solution. The goal is to block access to specific malicious URLs used for downloading malware, using advanced Suricata-compatible rules to inspect and filter web traffic.

## Key Concepts
* **AWS Network Firewall:** A managed service that provides high-availability network security to protect VPCs. It performs deep packet inspection (DPI).
* **Stateless Rules:** Fast inspection of individual packets (IP, port, protocol) without considering the connection context.
* **Stateful Rules:** Complex inspection that understands the traffic flow (context) and can look at application-layer data (like HTTP URIs).
* **Suricata:** An open-source intrusion detection system (IDS) and prevention system (IPS) engine that uses a specific rule language for traffic analysis.

## Task 2 & 3: Inspection and Rule Creation
To fix the vulnerability, we configured the firewall to be more "intelligent."

1. Updating the Firewall Policy
We modified the LabFirewallPolicy to change the default behavior for stateless packets:

* Action: Forward to stateful rule groups.
* *Why*? This ensures that every packet is inspected by the more advanced stateful engine instead of just being allowed through.

2. Creating a Stateful Rule Group
We created a rule group named `StatefulRuleGroup` using Suricata compatible rule strings:
```bash
drop http $HOME_NET any -> $EXTERNAL_NET 80 (msg:"MALWARE custom solution"; flow: to_server,established; classtype:trojan-activity; sid:2002001; content:"/data/js_crypto_miner.html";http_uri; rev:1;)

drop http $HOME_NET any -> $EXTERNAL_NET 80 (msg:"MALWARE custom solution"; flow: to_server,established; classtype:trojan-activity; sid:2002002; content:"/data/java_jre17_exec.html";http_uri; rev:1;)
```
* `drop`: The action to take when traffic matches.
* `http_uri`: The specific part of the packet to inspect (the URL path).
* `sid`: A unique Signature ID for the rule.

Task 4 & 5: Implementation and Validation
After attaching the `StatefulRuleGroup` to the `LabFirewall`, we tested the remediation.

## 💡 Pro-Tips for Network Security

1. **Drop vs. Reject:** - **Drop:** Discards the packet silently. The connection simply hangs until it times out. This is better for security as it provides no information to a potential attacker.
   - **Reject:** Sends a response back (like an ICMP unreachable). While helpful for debugging, it confirms to the sender that a firewall is active.
2. **The "Action Order" logic:** When configuring stateful rules, the **Action Order** ensures that `drop` rules are evaluated before `pass` rules. This prevents a general "allow all" rule from accidentally letting a malicious packet through.
3. **Deep Packet Inspection (DPI):** Unlike Security Groups (which only look at IP and Port), Network Firewall performs **DPI**. This allows it to look inside the HTTP header to find specific strings like `/data/js_crypto_miner.html`.
4. **Logging for Visibility:** In a production environment, always enable **Alert Logging** to Amazon CloudWatch. This allows you to track exactly which instances are attempting to access blocked malicious sites.
5. **Clean your environment:** Always use `rm` to delete test malware files once your validation is complete. Keeping dormant malicious strings—even for testing—can sometimes trigger secondary security alarms.
