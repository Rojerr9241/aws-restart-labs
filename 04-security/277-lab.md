# Lab 277: Systems Hardening with SSM Patch Manager

## Objective
Automate the lifecycle of operating system updates across a hybrid fleet of EC2 instances (Linux and Windows). This lab focuses on defining security baselines, organizing instances into patch groups, and verifying compliance through automated scanning.

## Key Concepts
* **Systems Manager (SSM):** A management service that helps you automatically collect software inventory, apply OS patches, and configure operating systems.
* **Patch Baseline:** A set of rules that defines which patches are approved for installation (e.g., "Approve all critical security updates 3 days after release").
* **Patch Group:** A way to associate EC2 instances with a specific patch baseline using Tags (e.g., `Key: Patch Group`, `Value: WindowsProd`).
* **Compliance:** The state of an instance being up-to-date according to its assigned baseline.

---

## Task 1: Patching Linux via Default Baselines
Linux instances often use the standard vendor baselines provided by AWS.

**Workflow:**
1. **SSM Fleet Manager:** Verified that instances were "Managed Nodes" (meaning they have the SSM Agent and correct IAM roles).
2. **Patch Now:** Executed an immediate scan and install operation.
3. **Targeting:** Instead of selecting IDs, we used **Tags** (`Patch Group: LinuxProd`). This is a best practice for scaling.
4. **Result:** Linux instances were updated using the `AWS-AmazonLinux2DefaultPatchBaseline`.

## Task 2 & 3: Custom Windows Patching
Windows environments often require more granular control over classifications (e.g., Security vs. Service Packs).

### 1. Creating a Custom Baseline
We created `WindowsServerSecurityUpdates` with specific rules:
* **Product:** Windows Server 2019.
* **Classification:** Security Updates.
* **Severity:** Critical and Important.
* **Auto-approval Delay:** 3 days (to allow for testing before global rollout).

### 2. Grouping and Execution
1. **Tagging:** Applied the tag `Patch Group: WindowsProd` to all three Windows instances.
2. **Association:** Linked the custom baseline to the `WindowsProd` group.
3. **Execution:** Triggered "Patch Now". Behind the scenes, SSM uses **Run Command** to execute the updates on the remote servers.

## 💡 Pro-Tips for Systems Hardening

1. **Maintenance Windows:** In production, never use "Patch Now" on live servers. Instead, schedule a **Maintenance Window** in SSM to run patches during low-traffic hours (e.g., Sunday at 2 AM).
2. **Reboot Hygiene:** Some patches require a reboot to take effect. Patch Manager can be configured to "Reboot if needed," ensuring the system is fully hardened.
3. **The SSM Agent:** For an EC2 instance to appear in Systems Manager, it **must** have the SSM Agent installed and an IAM Role with the `AmazonSSMManagedInstanceCore` policy.
4. **Pre-patching Snapshots:** Before a large patch operation, it is wise to take an **EBS Snapshot** of your instances. If a patch breaks an application, you can quickly revert to the previous state.
