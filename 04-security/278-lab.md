## Key Concepts
* **AWS KMS:** A managed service that makes it easy to create and control the keys used to encrypt your data.
* **Symmetric Encryption:** A method where the **same key** is used for both encryption and decryption. It is fast and ideal for large data sets.
* **Plaintext vs. Ciphertext:** - **Plaintext:** Data in its original, readable form.
    - **Ciphertext:** Encrypted data that is unreadable without the correct key.
* **Encryption Context:** Additional authenticated data used to provide an extra layer of security and integrity to the encryption process.

## Task 3: Practical Encryption and Decryption Workflow

In this task, we perform the actual cryptographic operations. The process involves creating sensitive data, transforming it into an unreadable format (Ciphertext), and then restoring it using the authorized KMS key.

### 1. Data Preparation
First, we create a secure environment and the mock sensitive files.
```bash
# Create multiple secret files
touch secret1.txt secret2.txt secret3.txt

# Add sensitive content to the first file
echo 'TOP SECRET 1!!!' > secret1.txt

# Create a specific directory for encrypted outputs
mkdir output
```
### 2. Setting the Key Variable
To avoid syntax errors and simplify the commands, we store the KMS ARN in a shell variable.

```bash
# Replace (KMS ARN) with your actual Key ARN from Task 1
keyArn=(arn:aws:kms:region:account-id:key/your-key-uuid)
```

### 3. Encrypting the Data (Plaintext to Ciphertext - Locking the Data)
The following command uses the AWS Encryption CLI to "lock" the file. Using the key ARN stored in the `$keyArn` variable. Each parameter adds a layer of security:

```bash
aws-encryption-cli --encrypt \
                     --input secret1.txt \
                     --wrapping-keys key=$keyArn \
                     --metadata-output ~/metadata \
                     --encryption-context purpose=test \
                     --commitment-policy require-encrypt-require-decrypt \
                     --output ~/output/.
```
* `--encryption-context purpose=test`: Binds the encrypted data to a specific "reason". You MUST provide this same context to decrypt it.
* `--commitment-policy`: Ensures the key used to encrypt is the same one used to decrypt, preventing certain types of cryptographic attacks.

### 4. Verification of Encryption
It is vital to confirm the command worked and the data is actually secured.
```bash
# Check the exit status (0 means success)
echo $?

# Confirm the new file exists in the output directory
ls output
# Expected: secret1.txt.encrypted

# Attempt to read the encrypted file
cd output
cat secret1.txt.encrypted
```
**Note:** When you run cat on the encrypted file, you should see unreadable "ciphertext" (garbage characters), confirming the data is protected.

### 5. Decrypting the Data (Ciphertext back to Plaintext - Unlocking the Data)
To restore the original information, we run the inverse operation. Note that we must provide the same **Key ARN** and **Encryption Context**.

```bash
aws-encryption-cli --decrypt \
                     --input secret1.txt.encrypted \
                     --wrapping-keys key=$keyArn \
                     --commitment-policy require-encrypt-require-decrypt \
                     --encryption-context purpose=test \
                     --metadata-output ~/metadata \
                     --max-encrypted-data-keys 1 \
                     --buffer \
                     --output .
```

* Result: The original message `"TOP SECRET 1!!!"` is restored into `secret1.txt.encrypted.decrypted.`


## 💡 Pro-Tips for Data Protection

1. **Symmetric vs. Asymmetric:** 
    - **Symmetric:** Fast and efficient; the same key locks and unlocks the data. Best for internal file and database encryption.
   - **Asymmetric:** Uses a Public key (to encrypt) and a Private key (to decrypt). Essential for digital signatures and secure communication between parties.
2. **Encryption Context:** Think of this as a "security label." If you encrypt a file with the context `purpose=test`, you **must** provide that exact context during decryption. If the context doesn't match, the decryption will fail even if you have the correct key.
3. **Verifying CLI Success:** In Linux, always run `echo $?` after a complex command. A return value of **0** confirms the operation was successful, while any other number indicates an error.
4. **Key Policy Power:** KMS keys are useless without a **Key Policy**. Even a Root Administrator cannot use a key unless the policy explicitly grants their IAM role permission to do so.
5. **Automatic Rotation:** For production environments, enable **Automatic Key Rotation**. AWS will update the underlying cryptographic material yearly without changing the Key ARN or requiring you to re-encrypt your data.
6.  **Exit Codes `$?`:** En administración de sistemas, nunca asumas que un comando funcionó porque no dio error visual. `echo $?` es tu mejor amigo en scripts para validar cada paso.
7.  **Metadata Output:** El archivo `~/metadata` generado contiene información técnica sobre la operación (algoritmo usado, IDs de llaves, etc.). Es útil para auditorías de seguridad.
8.  **Encadenamiento de Comandos:** Podrías ejecutar `aws-encryption-cli ... && echo "Success"` para que el mensaje solo aparezca si el código de salida es 0.
