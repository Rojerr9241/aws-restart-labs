# Lab 281: Monitoring an EC2 Instance with CloudWatch and SNS
**Course:** AWS re/Start | **Module:** Security & Monitoring

## Objective
The goal of this lab is to implement a robust monitoring and alerting system for AWS infrastructure. You will configure an Amazon CloudWatch alarm to detect anomalous CPU activity—simulating a security breach or malware execution—and trigger automated notifications via Amazon SNS (Simple Notification Service).

## Key Concepts

* **Amazon CloudWatch:** A monitoring and observability service that collects data in the form of logs, metrics, and events.
* **CloudWatch Alarms:** A feature that watches a single metric over a specified time period and performs actions based on the value of the metric relative to a threshold.
* **Amazon SNS (Simple Notification Service):** A managed pub/sub messaging service. In this context, it acts as the communication bridge between the alarm and the administrator's email.
* **CPU Stress Testing:** The process of deliberately increasing resource consumption to validate that monitoring systems and auto-scaling triggers are functioning correctly.
* **Security Monitoring:** Identifying "Red Flags" (like 100% CPU spikes) that may indicate unauthorized access, crypto-mining malware, or Denial of Service (DoS) conditions.

## Step-by-Step Instructions

### 1. Alerting Infrastructure (Amazon SNS)
Create the communication channel for security alerts.

1.  Navigate to the **Amazon SNS** console and create a **Standard Topic** named `MyCwAlarm`.
2.  Create a **Subscription**:
    * **Protocol:** Email.
    * **Endpoint:** Your personal email address.
3.  **Confirm Subscription:** Access your email inbox and click the "Confirm subscription" link sent by AWS.

> 📝 Technical Note: Subscription Confirmation
> An SNS subscription will remain in `Pending confirmation` status and will NOT send alerts until the owner of the endpoint manually clicks the confirmation link. This is a security measure to prevent spam.

### 2. Metric Observation and Alarm Configuration
Define the threshold for "anomalous" behavior.

1.  In **CloudWatch**, browse to **All Metrics** -> **EC2** -> **Per-Instance Metrics**.
2.  Locate the `Stress Test` instance and select the `CPUUtilization` metric.
3.  **Create Alarm:**
    * **Metric Period:** 1 Minute (for high-resolution monitoring).
    * **Statistic:** Average.
    * **Conditions:** Static | Greater than `60`.
4.  **Configure Actions:** Set the trigger to `In alarm` and send notifications to the `MyCwAlarm` SNS topic.
5.  **Name:** `LabCPUUtilizationAlarm`.

> 📝 Technical Note: CloudWatch Periods
> Standard monitoring is free at 5-minute intervals. Selecting a 1-minute period provides faster detection of security incidents but may incur additional costs in a production environment.

### 3. Simulating a Security Incident (Stress Test)
Simulate a malicious actor or application failure using the Linux `stress` utility.

1.  Connect to the `Stress Test` instance using **Session Manager**.
2.  Execute the stress command:
    ```bash
    sudo stress --cpu 10 -v --timeout 400s
    ```
    *Command explanation:* This utility spawns 10 workers spinning on `sqrt()` to deliberately max out the CPU cores for 400 seconds.

3.  In a second terminal tab, monitor the real-time load:
    ```bash
    top
    ```
    *Command explanation:* The `top` command provides a dynamic, real-time view of running processes and resource usage (CPU, Memory).

> [!TIP]
> **Evidence Placeholder:** Insert a screenshot of the `top` command showing 100% CPU usage or the CloudWatch graph crossing the 60% red line.

### 4. Visibility (CloudWatch Dashboards)
Create a persistent dashboard for operational health.

1.  In the CloudWatch sidebar, select **Dashboards** -> **Create dashboard** (`LabEC2Dashboard`).
2.  Add a **Line Widget** selecting the `CPUUtilization` metric for the `Stress Test` instance.
3.  Save the dashboard for quick access to real-time performance data.

## Pro-Tips for Real-World Scenarios

* 💡 **Pro-Tip: Avoid "Alarm Fatigue":** In production, setting an alarm at 60% might be too sensitive. Use **Anomaly Detection** (Machine Learning) instead of static thresholds to allow CloudWatch to learn the expected "normal" behavior of your app and only alert on true outliers.
* 💡 **Pro-Tip: Automated Remediation:** Don't just send an email. You can configure CloudWatch Alarms to trigger **EC2 Auto Recovery** or an **AWS Lambda** function to isolate an instance (quarantine) if a security threat is detected.
* 💡 **Pro-Tip: Instance Metadata:** If you see a CPU spike but don't know which instance it is, you can use the `InstanceId` dimension in CloudWatch to map metrics to specific business units using **Tags**.

## Useful Commands

| Command | Purpose |
| :--- | :--- |
| `sudo stress --cpu [n] --timeout [s]` | Generates synthetic load on 'n' CPU cores for 's' seconds. |
| `top` | Interactive process viewer (press 'q' to exit). |
| `htop` | (If installed) An improved, colorized version of `top` for easier monitoring. |
| `uptime` | Provides a quick look at the "Load Average" over the last 1, 5, and 15 minutes. |

## Cleanup

1.  **Delete the CloudWatch Alarm:** To prevent further SNS notifications.
2.  **Delete the SNS Topic and Subscriptions.**
3.  **Terminate the EC2 Instance:** Ensure the stress process is stopped and the instance is deleted to avoid costs.
