## Task 5: Adjusting S3 Bucket Permissions for Public Access

By default, Amazon S3 buckets are created with "Block Public Access" enabled and Access Control Lists (ACLs) disabled to enforce a secure-by-default posture. To transform the bucket into a public static website, we must manually adjust these security layers.

### 1. Disable Block Public Access (BPA)
This setting acts as a master "kill-switch" that prevents any public access, regardless of individual file permissions. We must disable it to allow the web server to serve content to the internet.

1.  In the **Amazon S3 Console**, choose your unique bucket name from the list.
2.  Navigate to the **Permissions** tab.
3.  Locate the **Block public access (bucket settings)** section and choose **Edit**.
4.  **Uncheck** the box for **Block all public access**.
5.  Choose **Save changes**.
6.  When prompted, enter `confirm` in the text field and choose **Confirm**.

### 2. Enable Access Control Lists (ACLs)
Standard S3 security uses IAM and Bucket Policies. However, to allow individual objects to be marked as "public-read" during the CLI upload process (Task 7), we must re-enable ACLs.

1.  Remaining on the **Permissions** tab, locate the **Object Ownership** section.
2.  Choose **Edit**.
3.  Select the radio button for **ACLs enabled**.
4.  A warning will appear regarding the restoration of ACLs. Select the checkbox for: 
    * **I acknowledge that ACLs will be restored.**
5.  Choose **Save changes**.

> 📝 **Technical Note:** While the modern AWS recommendation is to use **S3 Bucket Policies** and **IAM** for access control, enabling ACLs is still a widely used method for legacy applications and specific CLI workflows that require granular, object-level public permissions (using the `--acl public-read` flag).

## Task 7: Uploading Assets and Enabling Static Website Hosting

In this task, we use the high-level `aws s3` commands to configure the bucket as a web server and perform a bulk upload of the extracted assets. By applying public-read permissions at the object level, we ensure the site is accessible to the global internet.

### 1. Enabling Static Website Hosting via CLI
Before uploading files, we must tell S3 how to handle incoming web requests.

1.  **Configure the Index Document:** Replace `<my-bucket>` with your unique bucket name and run the following command:
    ```bash
    aws s3 website s3://<my-bucket>/ --index-document index.html
    ```
    * *Technical Note:* This command sets the "front door" of your website. When a user visits your bucket's root URL, S3 will automatically serve `index.html`.

### 2. Performing a Recursive Upload with Public ACLs
We use the `cp` (copy) command to transfer the entire website directory from the EC2 instance to the S3 bucket.

1.  **Upload Command:** Execute the following, ensuring you replace `<my-bucket>` with your bucket name:
    ```bash
    aws s3 cp /home/ec2-user/sysops-activity-files/static-website/ s3://<my-bucket>/ --recursive --acl public-read
    ```
    * *Command Breakdown:*
        * `--recursive`: Tells the CLI to include all files and subdirectories (css, images).
        * `--acl public-read`: Grants every uploaded object "Public Read" permission, bypassing the default private setting.

## 💡 Optional Challenge: Optimization with `s3 sync`

While the `aws s3 cp` command is effective for initial uploads, it is inefficient for updates because it re-uploads every file in the directory, regardless of whether the content has changed. To optimize this process, we can use the `aws s3 sync` command.

### 1. Understanding the `sync` Command
The `sync` command synchronizes the contents of a local directory and an S3 bucket by comparing the source and destination. It only uploads **new or modified files**, significantly reducing bandwidth and execution time.

### 2. Implementing the Efficiency Update
To optimize the deployment script, we replaced the copy command with the sync logic:

1.  **Modified the script:** We updated `update-website.sh` to use the following syntax:
    ```bash
    aws s3 sync /home/ec2-user/sysops-activity-files/static-website/ s3://<my-bucket>/ --acl public-read
    ```
2.  **Testing the Delta:** After making a small color change in `index.html` and running the script again, the terminal output showed that only the modified file was transmitted.

### 3. Comparison: `cp` vs `sync`

| Feature | `aws s3 cp --recursive` | `aws s3 sync` |
| :--- | :--- | :--- |
| **Behavior** | Uploads all files every time. | Only uploads "deltas" (modified files). |
| **Efficiency** | Lower (high overhead). | Higher (optimized for speed/bandwidth). |
| **Use Case** | Initial bulk transfers. | Continuous updates and CI/CD pipelines. |

> 💡 Pro-Tip: `Efficiency with s3 sync` - The `cp` command uploads everything every time. In a real-world scenario with thousands of images, this is inefficient. Using `aws s3 sync` is better because it compares the local source and the S3 destination, uploading only the files that have changed.
