# Lab 169: Orchestration and Automation with AWS Systems Manager ✅

## Objective
Utilize the various capabilities of AWS Systems Manager (SSM) to centralize operations. This includes automating software installations, managing application configurations through a global store, and accessing instances securely without SSH.

## Key Concepts
* **Fleet Manager:** A unified interface to manage and monitor the health and status of your entire fleet of managed nodes (EC2 and on-premises).
* **Run Command:** Allows you to remotely and securely manage the configuration of your managed instances at scale without logging into them.
* **Parameter Store:** A secure, hierarchical storage for configuration data and secrets management (passwords, strings, etc.).
* **Session Manager:** A browser-based shell that provides secure instance management without the need to open inbound ports (like Port 22 for SSH) or manage SSH keys.


## Task 1: Fleet Inventory Management
We used **Fleet Manager** to gather deep visibility into our managed instances without manual intervention.

**Detailed Workflow:**
1.  Navigate to **Systems Manager** > **Node Tools** > **Fleet Manager**.
2.  Choose **Account management** > **Set up inventory**.
3.  **Provide inventory details:** Name the association `Inventory-Association`. Create an automated task to track installed applications and OS versions.
4.  **Targets:** Choose **Manually selecting instances** and select the **Managed Instance**.
5.  **Execution:** Choose **Setup Inventory**.
6.  **Verification:**
    * Clicked the **Node ID** and navigated to the **Inventory tab**.
    * **Result:** We successfully retrieved a complete list of installed applications, OS versions, and network configurations without manually logging into each server.

> 📝 **Technical Note:** Fleet Manager eliminates the need to log into servers one by one to check compliance or software versions, providing a "single pane of glass" for the entire fleet.

## Task 2: Automated Deployment with Run Command
We deployed a full web stack (Apache, PHP, and the Dashboard App) using an automated SSM Document, removing the need for manual configuration scripts.

**Workflow:**
1.  Navigate to **Node Tools** > **Run Command**.
2.  **Selection:** Search for **Owner : Owned by me** to find the custom installation document and select it if not selected yet.
3.  **Targeting:** Manually selected the `Managed Instance`.
4.  **Security:** Disabled S3 logging (for lab speed) and executed the command.
5.  **What happened behind the scenes?**
    * The SSM Agent on the instance received the command via HTTPS.
    * It automatically installed **Apache**, **PHP**, and the **AWS SDK**.
    * It pulled the **Widget Manufacturing Dashboard** code and started the service.
6.  **Verification:** Accessed the `ServerIP` in a browser. The dashboard was live and functional.

## Task 3: Centralized Configuration (Parameter Store)
We demonstrated "Feature Flagging" or "Dark Launching" by using **Parameter Store** to control application behavior dynamically.

**Step-by-Step:**
1.  Navigate to **Application Management** > **Parameter Store**.
2.  **Create Parameter:**
    * **Name:** `/dashboard/show-beta-features`
    * **Type:** `String`
    * **Value:** `True`
3.  **Dynamic Update:** Refreshed the web dashboard.
4.  **Observation:** A **third chart (Beta feature)** immediately appeared. 
5.  **Conclusion:** This allows "Dark Launching" features—deploying code but only activating it when a parameter is switched in the cloud, without redeploying the app (The application is coded to "ask" the Parameter Store for instructions).

## Task 4: Secure Access with Session Manager
We accessed the instance shell directly through the browser (AWS Console), proving that **SSH (Port 22) is no longer required**.

**Execution Steps:**
1.  Navigate to **Node Management** > **Session Manager** > **Start session**.
2.  Connected to the `Managed Instance` via a secure browser-based terminal.
3.  **Commands Executed:**
    ```bash
    # Confirming the application files exist
    ls /var/www/html

    # Querying AWS Metadata and describing instances
    AZ=`curl -s http://169.254.169.254/latest/meta-data/placement/availability-zone`
    export AWS_DEFAULT_REGION=${AZ::-1}
    aws ec2 describe-instances
    ```

> 🔒 **Security Win:** Session Manager uses an encrypted tunnel over **Port 443 (HTTPS)**. This allows administrators to keep Port 22 closed in Security Groups, effectively removing the primary attack vector for brute-force SSH attacks.


## 💡 Pro-Tips for Automation

1. **Tag-Based Execution:** Instead of selecting instances manually in **Run Command**, use **Tags** (e.g., `Environment: Production`). This allows you to run a single task across hundreds of servers simultaneously, ensuring consistency across your fleet.
2. **The Power of Hierarchy:** In **Parameter Store**, always use a hierarchical naming convention (e.g., `/dev/db/password` vs `/prod/db/password`). This structure allows you to use IAM policies to restrict access to entire "folders" of sensitive data.
3. **SSH-less Security:** **Session Manager** is a security game-changer. Since it communicates over HTTPS (Port 443), you can keep Port 22 (SSH) closed in your Security Groups. This drastically reduces the attack surface of your instances.
4. **Infrastructure as Code (IaC) Ready:** Before clicking "Run" in Systems Manager, expand the **AWS command line interface command** section. This provides the exact CLI string you need to automate that same task via scripts or Lambda functions in the future.
5. **Auditing & Compliance:** Every command executed and every session started is logged in **AWS CloudTrail**. Unlike traditional SSH, Session Manager provides a complete, unalterable audit trail of who accessed the instance and what they did.
6. **Tag-Based Execution:** While we selected instances manually, in production you would target **Tags** (e.g., `Environment: Production`). This allows you to update 1,000 servers with a single Run Command.
