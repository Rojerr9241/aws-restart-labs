# Lab 160: Build Your DB Server and Interact With Your DB Using an App
**Course:** AWS re/Start | **Module:** Databases (Relational)

## Objective
The objective of this lab is to deploy a highly available, managed relational database using Amazon RDS (Relational Database Service). You will configure network security to allow communication between a web tier and a database tier, set up a Multi-AZ MySQL instance for fault tolerance, and validate the connection through a live web application.

## Key Concepts

* **Amazon RDS:** A managed service that handles routine database tasks such as patching, backups, and hardware provisioning.
* **Multi-AZ Deployment:** RDS automatically provisions and maintains a synchronous "standby" replica in a different Availability Zone. If the primary fails, RDS performs an automatic failover to the standby.
* **DB Subnet Group:** A collection of subnets (typically private) that you designate for your RDS DB instances in a VPC. It must span at least two Availability Zones.
* **Security Group Referencing:** The practice of allowing traffic in one security group by referencing another security group's ID, rather than using IP addresses.

## Step-by-Step Instructions

### 1. Database Security Configuration
Establish a firewall rule that permits the web server to communicate with the database.

1.  **Create Security Group:** Name it `DB Security Group` within the `Lab VPC`.
2.  **Inbound Rule:**
    * **Type:** MySQL/Aurora (Port 3306).
    * **Source:** Select `Web Security Group`.

> 📝 Technical Note: Security Group Nesting
> By referencing the `Web Security Group` as the source, you ensure that any EC2 instance associated with that group can talk to the database, regardless of its private IP address. This is a best practice for dynamic, auto-scaled environments.

### 2. Network Isolation (Subnet Groups)
Define where the database is allowed to reside within the VPC.

1.  **Create DB Subnet Group:** Name it `DB Subnet Group`.
2.  **Configuration:** Select the two available Availability Zones and their corresponding private subnets (`10.0.1.0/24` and `10.0.3.0/24`).

> 💡 Pro-Tip: Database Placement
> Databases should almost always be placed in **Private Subnets**. They do not need direct internet access; they only need to be reachable by the application servers or a bastion host.

### 3. Provisioning the RDS Instance
Deploy a managed MySQL engine with high availability.

1.  **Engine:** MySQL (Standard create).
2.  **Availability:** Select **Multi-AZ DB Instance**.
3.  **Settings:**
    * **Identifier:** `lab-db`
    * **Credentials:** User `main` / Password `lab-password`.
4.  **Connectivity:**
    * **VPC:** `Lab VPC`.
    * **Security Group:** Choose existing `DB Security Group`.
5.  **Additional Configuration:** Set the initial database name to `lab`.

> 📝 Technical Note: Multi-AZ vs. Read Replicas
> **Multi-AZ** is for High Availability (HA) and disaster recovery; it is a synchronous copy. **Read Replicas** are for performance scaling and are typically asynchronous.

### 4. Application Integration
Connect the front-end web application to the RDS back-end.

1.  **Retrieve Endpoint:** Go to the RDS console, select `lab-db`, and copy the **Endpoint** (DNS address).
2.  **Access Web App:** Open the `WebServer IP` in your browser.
3.  **RDS Connection:**
    * Click the **RDS** link in the app.
    * Paste the **Endpoint**, DB Name (`lab`), and credentials.
4.  **Validate:** Add a contact to the Address Book to confirm that "Writes" are succeeding.

> **Command explanation:** When you click "Submit", the web application uses a database driver (like PHP's PDO or Python's MySQLdb) to establish a TCP connection to the RDS endpoint on port 3306 and execute SQL `INSERT` or `CREATE TABLE` commands.

## Pro-Tips for Real-World Scenarios

* 💡 **Pro-Tip: Use Secrets Manager:** In production, never type database passwords into a web form or hardcode them in scripts. Use **AWS Secrets Manager** to store and rotate credentials securely.
* 💡 **Pro-Tip: Enhanced Monitoring:** In this lab, we disabled Enhanced Monitoring for speed. In the real world, enabling it provides high-resolution metrics (1-second intervals) which are vital for diagnosing database performance bottlenecks.
* 💡 **Pro-Tip: Storage Auto-scaling:** For unpredictable workloads, enable **Storage Autoscaling**. RDS will automatically increase the allocated storage if the database runs out of space, preventing downtime.

## Useful Commands / Reference

| Parameter | Value in this Lab |
| :--- | :--- |
