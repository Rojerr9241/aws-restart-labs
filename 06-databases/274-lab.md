# Lab 274: Introduction to Amazon Aurora *

## Objective
Deploy and configure a high-performance relational database using **Amazon Aurora**. This lab covers the full lifecycle of a cloud database: provisioning a managed cluster, establishing secure connectivity from an EC2 instance, and performing database schema creation and data querying.

## Key Concepts
* **Amazon Aurora:** A MySQL and PostgreSQL-compatible relational database built for the cloud. It is up to 5x faster than standard MySQL.
* **Cluster Endpoint:** The "Writer" endpoint used for all write operations (INSERT, UPDATE, DELETE). It automatically points to the primary instance.
* **Reader Endpoint:** Used to load-balance read-only traffic across available Aurora Replicas.
* **Managed Service:** AWS handles time-consuming tasks like patching, backups, and failure detection.

## 💡 Pro-Tips for Amazon Aurora

1. **Endpoint Intelligence:** Always use the **Cluster Endpoint** (Writer) for your application’s main connection. If the primary database fails, Aurora automatically promotes a replica to primary, and the DNS endpoint updates to point to the new master. You won't need to change a single line of code in your app!
2. **Read Scaling:** If your application is "read-heavy" (lots of SELECTs), use the **Reader Endpoint**. It automatically load-balances traffic across all your Aurora Replicas, preventing the primary instance from becoming overwhelmed.
3. **Storage Auto-Scaling:** Unlike standard RDS, you don't need to pre-provision storage for Aurora. It starts at 10GB and automatically grows in 10GB increments up to 128TB as your data expands. You only pay for what you actually use.
4. **Security Best Practice:** In a production environment, never give your Aurora instance **Public Access**. Always keep it in private subnets and use a **Bastion Host** or **Session Manager** (like our Command Host) to connect securely.
5. **Snapshot vs. Backup:** Aurora performs continuous, incremental backups to S3 automatically. However, before a major "risky" SQL operation, manually take a **DB Snapshot**. It's nearly instantaneous and gives you a point-in-time recovery "safety net."
