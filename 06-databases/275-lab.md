## Objective
The goal of this lab is to explore the fundamental operations of Amazon DynamoDB, a serverless NoSQL database. You will learn how to design a table with a composite primary key, manage schema-less data (items and attributes), and understand the performance differences between Query and Scan operations.

## Key Concepts

* **NoSQL Database:** A non-relational database that allows for flexible schemas, making it ideal for rapid development and massive horizontal scaling.
* **Partition Key (PK):** Also known as a Hash Key, it is used to distribute data across multiple partitions for scalability.
* **Sort Key (SK):** Also known as a Range Key, it allows you to store multiple items with the same Partition Key in a sorted order.
* **Composite Primary Key:** The combination of a Partition Key and a Sort Key (`Artist` + `Song` in this lab).
* **Items & Attributes:** An "Item" is a row, and an "Attribute" is a column. Unlike SQL, items in the same table can have different attributes.
* **Query vs. Scan:**
    * **Query:** Efficiently finds items using only the Primary Key. It is fast and cost-effective.
    * **Scan:** Examines every single item in the table. It is slow and expensive for large datasets.

## Task 4: Query vs. Scan
Understanding the difference between a Query and a Scan is critical for performance and cost optimization.

### 4.1 Performing a Query (High Efficiency)
A **Query** searches only based on the Partition Key, making it the fastest way to retrieve data.
1. Expand **Scan/Query items** and select **Query**.
2. **Partition key (Artist):** `Psy`
3. **Sort key (Song):** `Gangnam Style`
4. Choose **Run**. The result appears instantly because DynamoDB knows exactly which partition to look at.

### 4.2 Performing a Scan (Full Table Search)
A **Scan** examines every single item in the table, which is less efficient for large datasets.
1. Change the selection from Query to **Scan**.
2. Expand **Filters** and enter:
    * **Attribute name:** `Year`
    * **Type:** `Number`
    * **Value:** `1971`
3. Choose **Run**.

> 📝 **Technical Note:** Always prioritize **Queries** over Scans. Scans consume more Read Capacity Units (RCUs) and can become very slow as your table grows.

## 💡 Pro-Tips for Real-World Scenarios

1. **Partition Key Selection:** Choosing a high-cardinality Partition Key (like a UserID or OrderID) is a Best Practice to avoid **"Hot Partitions"**, which occur when a single physical partition receives too much traffic, causing performance bottlenecks.
2. **Avoid Scans in Production:** Scans consume Read Capacity Units (RCUs) for every item in the table. As your table grows to millions of rows, a Scan can become extremely slow and expensive. Always try to model your data to use **Queries**.
3. **Schema-less Flexibility:** Unlike SQL, you can add a `BPM` attribute to one song and a `Producer` attribute to another without altering the table structure. This makes DynamoDB ideal for rapidly evolving applications.
4. **Provisioned vs. On-Demand:** For this lab, we used **Provisioned Capacity**. In production, if your traffic is unpredictable, **On-Demand mode** is often better as it scales instantly without managing "Read/Write Capacity Units."
5. **Use Global Secondary Indexes (GSI):** If you need to search by an attribute that isn't the Primary Key (e.g., searching by `Year`), create a GSI. This creates a "shadow copy" of your table with a different Partition Key to allow fast Queries.
6. **TTL (Time to Live):** You can set a TTL attribute to automatically delete old items (like session logs or temporary cart data) at no extra cost, helping you manage storage and compliance.
